# Crowdwide Roadmap

## Completed

- Posts, articles, polls, drafts, scheduled publishing, media uploads, alt text, hashtags, mentions, quote posts, and linked post replies.
- Edit/delete controls for owned posts and comments.
- Likes, comment likes, reactions, bookmarks, sharing, nested replies, and no-reload AJAX interactions.
- Private/public communities, join requests, roles, moderators, banned words, post approval, pinned posts, guidelines, and community feeds.
- Profiles with banners, avatars, bios, links, privacy controls, followers/following, saved posts, activity, likes, and comments.
- Email verification, password reset, login lockouts, TOTP 2FA, recovery codes, session/device management, CSRF, Helmet, and rate limits.
- Reports, moderation queues, admin approval, audit logs, account suspension, and data export/deletion.
- Direct messages, group conversations, notification preferences/grouping, mention notifications, and security notifications.
- Feed discovery, personalized feeds, viral/new tabs, trending hashtags, recommendations, search filters, RSS, and `/api/v1/posts`.
- Production indexes, centralized error handling, database-aware health checks, and scheduled publication worker.
- User mute/unmute controls applied to feeds, search, notifications, and profile actions.
- Unanswered-post discovery filter in search.
- Content-warning labels with blurred content and in-place reveal controls.
- Admin console functions (post/community/user moderation, pinning, settings, moderator approval queue) audited end-to-end; the "pin post to community" control never persisted or reflected state and is now fixed. (#8)
- Group chat (create/list/thread/send) audited end-to-end; a membership-check bug that 404'd every member out of their own group thread is fixed. (#10)
- Security emails: new-sign-in alerts (now firing correctly for both password and 2FA logins), password-changed, 2FA enabled/disabled, recovery-codes-regenerated, and a real password-reset email (previously just console-logged) — all respecting the existing per-user "security notifications" preference toggle. (#9)
- Automated tests: permission/role-middleware, upload-validation, and push-service unit tests (DB-free, run via `npm test`, 30/30 passing), plus a route-level/end-to-end signup-verify-login-post and admin-permission suite (`npm run test:e2e`, requires a MongoDB connection - see Known Gaps). (#4)
- Browser push notifications (likes, comments, replies, follows, mentions) with explicit per-device opt-in from Settings, a service worker, and graceful no-op when VAPID keys aren't configured. Dead subscriptions are pruned automatically. Unit-tested (see above); the live browser flow (permission prompt, service worker registration, an actual push arriving) has not been exercised in a real browser - see Known Gaps. (Next Priorities #1)
- Auth reliability: a mail-provider hiccup (timeout, expired OAuth token, rate limit) could make login show "temporarily unavailable" with correct credentials, make registration show a false failure after the account was already created, and made 2FA login/password-reset hang indefinitely with no response (Express 4 doesn't auto-catch async route rejections, and none of those handlers had try/catch). Mail sending is now best-effort everywhere - it logs and continues instead of throwing - and every previously-unguarded auth/2FA/password-change handler now has proper error handling instead of hanging. Verified with 5 new unit tests simulating a down mail provider.
- Richer article/post rendering: paragraphs, "# heading" lines, "- list" lines, and **bold**/*italic* are now rendered as real HTML instead of one plain-text blob, with HTML always escaped before any formatting is applied (XSS-safe). Unit-tested (10 tests) including an explicit script-injection attempt.
- Media captions and transcripts: `caption` (shown under the media) and `transcript` (expandable, for audio/video) fields added end-to-end - schema, composer form, and display. Also fixed: the composer's file input was missing the `multiple` attribute, so "upload up to 2 files" was never actually reachable in the browser despite the backend supporting it; and alt text had no way to be entered anywhere in the UI despite being listed as done. Note: like the pre-existing alt-text field, caption/transcript are one field per post (applied to every file in that post), not per individual file - see Known Gaps.
- Link previews: the first URL in a post (when the post has no attached media) is unfurled in the background - title/description/image/site via Open Graph tags, falling back to `<title>`/`<meta name="description">` - and shown as a card. Fetching is fire-and-forget (never blocks or delays posting, the same lesson as the auth-reliability fix above), time-capped, size-capped (reads at most 200KB), and has a baseline SSRF guard blocking localhost/private/link-local hosts. 18 unit tests cover URL extraction, the SSRF guard, HTML parsing, and full end-to-end parsing against a mocked fetch - see Known Gaps for what live testing would still need to confirm.
- Critical moderation security fix: admin-imposed user suspension and the auth system's own failed-password lockout were stored in the same field (`loginLockedUntil`), so 5 wrong password guesses against a suspended account would silently overwrite a multi-day suspension with a 15-minute self-clearing lockout - anyone could defeat a suspension in minutes just by guessing wrong on purpose. Split into separate `suspendedUntil` (admin-imposed, immune to failed-login handling) and `loginLockedUntil` (self-clearing, failed-password only) fields, with distinct user-facing messaging for each. Covered by a new e2e regression test that explicitly proves 5 failed attempts no longer touches the suspension.
- Temporary posting restrictions ("mutes"): a moderator-imposed, time-limited block on creating new posts/comments - distinct from both full suspension (blocks login entirely) and the pre-existing personal "muted users" preference (only affects what the muting user sees, not what the muted user can do - kept clearly separate to avoid confusing the two "mute" concepts). Enforced in both post and comment creation, with an admin UI (24h/72h/7-day/lift). Unit-tested.
- Registration CAPTCHA: a lightweight built-in arithmetic challenge (single-use, 10-minute expiry) to deter naive scripted signups. Not a production-grade CAPTCHA - no external service key (reCAPTCHA/hCaptcha/Turnstile) is available in this environment - see Known Gaps. Unit-tested.
- Spam detection: blocks a user from posting the exact same body text twice within 10 minutes. Unit-tested against a mocked Post model.
- Evidence attachments on reports: an optional screenshot can be attached when reporting a post, shown to admins/moderators alongside the report. Reuses the existing upload-validation pattern (2MB limit, image-only), unit-tested.

## Known Gaps

- Push notifications are unit-tested but the live browser flow (permission prompt, service worker registration/subscription, a push actually arriving on a device) has not been exercised in a real browser - this sandbox has no browser. Also requires generating real VAPID keys (`npx web-push generate-vapid-keys`) and setting them in the deployment environment before it does anything.
- Link previews: the SSRF guard checks the hostname/IP as written in the URL, not the IP it actually resolves to, so it does not defend against DNS rebinding (a hostname that resolves to a private IP only at fetch time). The whole feature is unit-tested against a mocked fetch but has not made a real HTTP request in this sandbox - worth trying against a few real URLs (including ones that redirect, and ones with no Open Graph tags at all) before relying on it. Also, since fetching is fire-and-forget, a freshly-created post's preview may not be visible until the next page load/refresh.
- Media alt text, caption, and transcript are one field per post (applied to every uploaded file in that post) rather than per individual file - fine for the common one-file case, less precise when two files are attached with different content.
- Registration CAPTCHA is a simple arithmetic challenge, not a managed service - it stops naive scripted signups, not a determined attacker or a vision-capable bot. Swap in a real CAPTCHA service if bot signups become a real problem.
- Moderation appeals are not implemented - a suspended/restricted/warned user currently has no in-app way to contest the action other than contacting a moderator directly.
- The `test:e2e` suite (signup/posting flow, admin route permissions, the suspension-bypass regression test) is written and wired into `npm run test:e2e`, but has not been executed successfully in this environment - it needs network access to download a MongoDB binary (via mongodb-memory-server) or a MONGODB_URI pointing at a real database. Run it locally to confirm before relying on it in CI.
- Monitoring, backups, CI/staging, and upload virus scanning require deployment infrastructure.
