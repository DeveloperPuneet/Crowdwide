- Automated tests: permission/role-middleware, upload-validation, push-service, posting-restriction, spam-detection, captcha, link-preview, rich-body-rendering, mailer-resilience, appeal-submission, logger, alerting, and virus-scan unit tests (DB-free, run via `npm test`, 119/119 passing as of this pass), plus a route-level/end-to-end suite covering signup-verify-login-post, admin permissions, the suspension bypass, and the full appeal lifecycle (`npm run test:e2e`, requires a MongoDB connection - see Known Gaps). (#4)
- Browser push notifications (likes, comments, replies, follows, mentions) with explicit per-device opt-in from Settings, a service worker, and graceful no-op when VAPID keys aren't configured. Dead subscriptions are pruned automatically. Unit-tested (see above); the live browser flow (permission prompt, service worker registration, an actual push arriving) has not been exercised in a real browser - see Known Gaps. (Next Priorities #1)
- Auth reliability: a mail-provider hiccup (timeout, expired OAuth token, rate limit) could make login show "temporarily unavailable" with correct credentials, make registration show a false failure after the account was already created, and made 2FA login/password-reset hang indefinitely with no response (Express 4 doesn't auto-catch async route rejections, and none of those handlers had try/catch). Mail sending is now best-effort everywhere - it logs and continues instead of throwing - and every previously-unguarded auth/2FA/password-change handler now has proper error handling instead of hanging. Verified with 5 new unit tests simulating a down mail provider.
- Richer article/post rendering: paragraphs, "# heading" lines, "- list" lines, and **bold**/*italic* are now rendered as real HTML instead of one plain-text blob, with HTML always escaped before any formatting is applied (XSS-safe). Unit-tested (10 tests) including an explicit script-injection attempt.
- Media captions and transcripts: `caption` (shown under the media) and `transcript` (expandable, for audio/video) fields added end-to-end - schema, composer form, and display. Also fixed: the composer's file input was missing the `multiple` attribute, so "upload up to 2 files" was never actually reachable in the browser despite the backend supporting it; and alt text had no way to be entered anywhere in the UI despite being listed as done. Note: like the pre-existing alt-text field, caption/transcript are one field per post (applied to every file in that post), not per individual file - see Known Gaps.
- Link previews: the first URL in a post (when the post has no attached media) is unfurled in the background - title/description/image/site via Open Graph tags, falling back to `<title>`/`<meta name="description">` - and shown as a card. Fetching is fire-and-forget (never blocks or delays posting, the same lesson as the auth-reliability fix above), time-capped, size-capped (reads at most 200KB), and has a baseline SSRF guard blocking localhost/private/link-local hosts. 18 unit tests cover URL extraction, the SSRF guard, HTML parsing, and full end-to-end parsing against a mocked fetch - see Known Gaps for what live testing would still need to confirm.
- Critical moderation security fix: admin-imposed user suspension and the auth system's own failed-password lockout were stored in the same field (`loginLockedUntil`), so 5 wrong password guesses against a suspended account would silently overwrite a multi-day suspension with a 15-minute self-clearing lockout - anyone could defeat a suspension in minutes just by guessing wrong on purpose. Split into separate `suspendedUntil` (admin-imposed, immune to failed-login handling) and `loginLockedUntil` (self-clearing, failed-password only) fields, with distinct user-facing messaging for each. Covered by a new e2e regression test that explicitly proves 5 failed attempts no longer touches the suspension.
- Temporary posting restrictions ("mutes"): a moderator-imposed, time-limited block on creating new posts/comments - distinct from both full suspension (blocks login entirely) and the pre-existing personal "muted users" preference (only affects what the muting user sees, not what the muted user can do - kept clearly separate to avoid confusing the two "mute" concepts). Enforced in both post and comment creation, with an admin UI (24h/72h/7-day/lift). Unit-tested.
- Registration CAPTCHA: a lightweight built-in arithmetic challenge (single-use, 10-minute expiry) to deter naive scripted signups. Not a production-grade CAPTCHA - no external service key (reCAPTCHA/hCaptcha/Turnstile) is available in this environment - see Known Gaps. Unit-tested.
- Spam detection: blocks a user from posting the exact same body text twice within 10 minutes. Unit-tested against a mocked Post model.
- Evidence attachments on reports: an optional screenshot can be attached when reporting a post, shown to admins/moderators alongside the report. Reuses the existing upload-validation pattern (2MB limit, image-only), unit-tested.
- Moderation appeals: suspended users (who can't log in to reach Settings at all) can appeal from a new public page linked off the login screen; posting-restricted or warned users appeal from a new "Moderation" section in Settings. Admins get a new "Appeals" tab that shows the appeal message and, on approval, automatically lifts the underlying suspension/restriction/warning and logs it to the audit trail; denying leaves it in place. 11 unit tests cover submission logic (mocked models); an e2e test covers the full lifecycle - blocked login, public appeal, admin approval, working login afterward - and a second e2e test confirms a denied appeal leaves the suspension in place (see Known Gaps for e2e caveats). Caught and fixed a mistake of my own along the way: an edit that accidentally deleted an unrelated required route import, which would have crashed the whole app on boot - caught by actually booting the app with supertest after the change, not just reviewing the diff.
- Structured logging, monitoring/alerts, backup/restore checks, CI, staging, and upload virus scanning: a JSON structured logger replaced ~28 scattered console.log/error calls app-wide; unhandled 5xx errors email an admin address (rate-limited to avoid alert storms); uploads are scanned through a ClamAV daemon's INSTREAM protocol when configured, failing open on scanner errors; a GitHub Actions CI workflow runs the unit suite on every push and the full e2e suite against a real MongoDB service container; backup/restore-verification scripts wrap mongodump/mongorestore, with the restore check proving a backup is actually restorable (not just that the file exists) by restoring into a scratch database and sanity-checking it; staging is covered as deployment guidance in a new DEPLOYMENT.md, since it's not something code alone provides. 25 new unit tests across logging/alerting/virus-scanning; the CI workflow was validated by actually parsing it with js-yaml, not just reviewed by eye. Caught two of my own mistakes mid-edit this round (a wrong relative import path, and an accidentally-deleted guard line) by re-running node --check and booting the app after each change rather than trusting the diff - see Known Gaps for what still needs verifying against real infrastructure.
- Monetization placeholder: a public `/premium` page explaining nothing is for sale yet, what has to be true first (safety/moderation systems proven, reliability holding up under real traffic, an actual community using Crowdwide day to day), and that the core experience won't go behind a paywall - linked from both footers and the sitemap.
- Search history and account history: recent searches are saved per user (capped at 20, deduped, clearable) and shown on the empty search page; a new `AccountEvent` model logs every security-relevant self-event (logins, password/2FA changes, suspensions/restrictions applied or lifted, warnings, appeals) across every place those already happen, surfaced as a readable timeline in a new Settings > History page.
- RSS feeds for public profiles (`/u/:id/rss.xml`) and communities (`/communities/:slug/rss.xml`), alongside the existing site-wide feed. Building these surfaced a severe, systemic bug - see the entry right below this one - so all three feeds, plus every other post-listing surface in the app, now correctly respect private-community membership.
- CRITICAL FIX - private communities were not actually private: posts in a private community were fully visible to any logged-in user (and via the public API, any anonymous visitor) through the community page, direct post URLs, the main dashboard feed and its tabs, search, profile pages (including the Comments tab, via the parent post), the public `/api/v1/posts` API (including by passing `?community=<id>` directly), and the global RSS feed - and could even be liked/commented/reacted to/replied to/quoted/shared/voted on/reported by non-members, since the shared `canAccessPost` authorization gate used by ~12 interaction endpoints had no community-privacy awareness at all. Fixed comprehensively: one shared, unit-tested utility (`getRestrictedCommunityIds`) applied to every post query listed above, plus a rewritten community-aware `canAccessPost`, plus a proper "members only" state on the community page instead of leaking content. Found while auditing communities per the standing "full check" item. 21 new unit tests plus a full end-to-end regression test proving the leak is closed through every surface (with a sanity check that actual members still see everything normally). Also fixed, found along the way: four of the same "unguarded async handler can hang forever" bugs from earlier this session, in the very same RSS/API endpoints, and a `limit=0` edge case in `/api/v1/posts` that silently fell back to the default instead of clamping to 1.

## Known Gaps

- Push notifications are unit-tested but the live browser flow (permission prompt, service worker registration/subscription, a push actually arriving on a device) has not been exercised in a real browser - this sandbox has no browser. Also requires generating real VAPID keys (`npx web-push generate-vapid-keys`) and setting them in the deployment environment before it does anything.
- Link previews: the SSRF guard checks the hostname/IP as written in the URL, not the IP it actually resolves to, so it does not defend against DNS rebinding (a hostname that resolves to a private IP only at fetch time). The whole feature is unit-tested against a mocked fetch but has not made a real HTTP request in this sandbox - worth trying against a few real URLs (including ones that redirect, and ones with no Open Graph tags at all) before relying on it. Also, since fetching is fire-and-forget, a freshly-created post's preview may not be visible until the next page load/refresh.
- Media alt text, caption, and transcript are one field per post (applied to every uploaded file in that post) rather than per individual file - fine for the common one-file case, less precise when two files are attached with different content.
- Registration CAPTCHA is a simple arithmetic challenge, not a managed service - it stops naive scripted signups, not a determined attacker or a vision-capable bot. Swap in a real CAPTCHA service if bot signups become a real problem.
- Moderation appeals are only resolvable by admins, not moderators - a reasonable scope choice for now (undoing a suspension is an admin-level action already) but worth revisiting if the appeal volume grows. The whole feature's e2e coverage (see below) hasn't actually been run.
- The `test:e2e` suite (signup/posting flow, admin route permissions, the suspension-bypass regression test, the full appeal lifecycle) is written and wired into `npm run test:e2e`, but has not been executed successfully in this environment - it needs network access to download a MongoDB binary (via mongodb-memory-server) or a MONGODB_URI pointing at a real database. Run it locally to confirm before relying on it in CI.
- Monitoring/alerting, backups/restore, CI, and virus scanning are all unit-tested (or YAML-validated, for the CI workflow) but none have run against real infrastructure in this sandbox: no ClamAV daemon, no mongodump/mongorestore binaries, no GitHub Actions runner, and no real SMTP alert delivery were available here. See DEPLOYMENT.md for what to verify before relying on each in production. Virus scanning fails OPEN on a scanner outage (allows the upload rather than blocking it) - a deliberate trade-off, documented in DEPLOYMENT.md, that a stricter deployment may want to flip.
- "Staging" has documentation only (DEPLOYMENT.md) - there's no staging-specific code, since staging is fundamentally about running a second deployed environment with separate env vars, not something the codebase itself provides.
