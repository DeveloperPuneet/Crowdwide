# Crowdwide Roadmap

## Completed

- Advertiser and campaign foundation — approved advertiser registration, campaign submission flow, moderation lifecycle, CTR tracking, and budget controls.
- Advertiser campaign dashboard — advertiser applications and verification, draft creation, Waves-funded submission, admin campaign approval/rejection, pause/resume/cancellation controls, and per-campaign/aggregate performance and budget statistics.
- Staged advertisement campaign moderation — moderators review submitted campaigns first, record a reasoned clear/flag recommendation with an audit log, and admins make the final decision; campaigns cannot be approved without a clear moderator review.
- Staged advertiser application moderation — moderator screening with a recorded clear/flag reason and audit log, followed by final admin approval/rejection; approval is blocked unless moderators clear the application.
- Prohibited-ad policy screening — moderator campaign review records specific flags for adult-only/18+, erotic or sexually explicit content, gambling/betting, pornography, and other inappropriate ads; every category must be checked before a campaign can be cleared for admin approval.
- Admin campaign suspension and removal — admins can suspend active/approved campaigns with a logged reason, reinstate them only to approved (requiring advertiser activation), or remove/cancel and refund unused funded Waves; advertisers cannot reactivate suspended campaigns.
- Advertiser policy and terms — public, linked advertising terms cover advertiser requirements, prohibited content, staged moderation, Waves escrow, anti-manipulation rules, and launch limitations; current terms acceptance is recorded and required before campaign creation or funding, and visible to moderators/admins.
- Waves-funded campaign budgets — campaigns start as drafts, escrow the configured Waves budget on submission, and record funding/refund entries in the Waves ledger. Cancellation, rejection, and completion refund the remaining budget once.
- Campaign daily budget enforcement — budget spend is rejected when it would exceed the configured daily cap and the daily counter resets on the next calendar day.
- Waves currency foundation — user balances, ledger entries, credit/debit/transfer services, admin adjustments with reasons, visible signed-in balance, and wallet transaction history.
- User Waves transfers — wallet send form and recipient lookup, with self-transfer/recipient suspension checks plus configurable per-transfer and daily limits.
- Initial Waves rewards — configurable random post/comment reward ranges, admin controls, and a configurable daily earning cap.
- Received-engagement Waves rewards — configurable rewards for genuine post likes and comments, with self-interaction rejection and durable duplicate-claim keys.
- Community and quest Waves rewards — configurable rewards for joining/creating communities and completing quests, once per user/action target and subject to the daily cap.
- Community monetization application foundation — owner eligibility checklist and application, configurable post/like/comment thresholds with server-side enforcement, and admin review/approval workflow.
- Community monetization status and ad-configuration scaffolding.
- Community Galaxy — Interactive Community Discovery Map 🌐
- Rising Communities Radar — Discover Growing Communities 📡

- Group chat (create/list/thread/send) audited end-to-end; a membership-check bug that 404'd every member out of their own group thread is fixed. (#10)
- Security emails: new-sign-in alerts (now firing correctly for both password and 2FA logins), password-changed, 2FA enabled/disabled, recovery-codes-regenerated, and a real password-reset email (previously just console-logged) — all respecting the existing per-user "security notifications" preference toggle. (#9)
- Automated tests: permission/role-middleware, upload-validation, push-service, posting-restriction, spam-detection, captcha, link-preview, rich-body-rendering, mailer-resilience, appeal-submission, logger, alerting, and virus-scan unit tests (DB-free, run via `npm test`, 119/119 passing as of this pass), plus a route-level/end-to-end suite covering signup-verify-login-post, admin permissions, the suspension bypass, and the full appeal lifecycle (`npm run test:e2e`, requires a MongoDB connection - see Known Gaps). (#4)
- Browser push notifications (likes, comments, replies, follows, mentions) with explicit per-device opt-in from Settings, a service worker, and graceful no-op when VAPID keys aren't configured. Dead subscriptions are pruned automatically. Unit-tested (see above); the live browser flow (permission prompt, service worker registration, an actual push arriving) has not been exercised in a real browser - see Known Gaps. (Next Priorities #1)
- Auth reliability: a mail-provider hiccup (timeout, expired OAuth token, rate limit) could make login show "temporarily unavailable" with correct credentials, make registration show a false failure after the account was already created, and made 2FA login/password-reset hang indefinitely with no response (Express 4 doesn't auto-catch async route rejections, and none of those handlers had try/catch). Mail sending is now best-effort everywhere - it logs and continues instead of throwing - and every previously-unguarded auth/2FA/password-change handler now has proper error handling instead of hanging. Verified with 5 new unit tests simulating a down mail provider.
- Richer article/post rendering: paragraphs, "# heading" lines, "- list" lines, and **bold**/*italic* are now rendered as real HTML instead of one plain-text blob, with HTML always escaped before any formatting is applied (XSS-safe). Unit-tested (10 tests) including an explicit script-injection attempt.
- Media alt text, captions and transcripts, entered per attached file (up to two files per post) - schema, composer, and display. Older single-value posts still work. Unit-tested.
- Link previews: the first URL in a post (when the post has no attached media) is unfurled in the background - title/description/image/site via Open Graph tags, falling back to `<title>`/`<meta name="description">` - and shown as a card. Fetching is fire-and-forget (never blocks or delays posting, the same lesson as the auth-reliability fix above), time-capped, size-capped (reads at most 200KB), and has a baseline SSRF guard blocking localhost/private/link-local hosts. 18 unit tests cover URL extraction, the SSRF guard, HTML parsing, and full end-to-end parsing against a mocked fetch - see Known Gaps for what live testing would still need to confirm.
- Critical moderation security fix: admin-imposed user suspension and the auth system's own failed-password lockout were stored in the same field (`loginLockedUntil`), so 5 wrong password guesses against a suspended account would silently overwrite a multi-day suspension with a 15-minute self-clearing lockout - anyone could defeat a suspension in minutes just by guessing wrong on purpose. Split into separate `suspendedUntil` (admin-imposed, immune to failed-login handling) and `loginLockedUntil` (self-clearing, failed-password only) fields, with distinct user-facing messaging for each. Covered by a new e2e regression test that explicitly proves 5 failed attempts no longer touches the suspension.
- Temporary posting restrictions ("mutes"): a moderator-imposed, time-limited block on creating new posts/comments - distinct from both full suspension (blocks login entirely) and the pre-existing personal "muted users" preference (only affects what the muting user sees, not what the muted user can do - kept clearly separate to avoid confusing the two "mute" concepts). Enforced in both post and comment creation, with an admin UI (24h/72h/7-day/lift). Unit-tested.
- Registration bot protection: built-in arithmetic challenge (single-use, 10-minute expiry) plus an invisible honeypot field and a minimum-fill-time check, with optional Cloudflare Turnstile (managed CAPTCHA) when `TURNSTILE_SITE_KEY`/`TURNSTILE_SECRET_KEY` are set. Unit-tested.
- Spam detection: blocks a user from posting the exact same body text twice within 10 minutes. Unit-tested against a mocked Post model.
- Evidence attachments on reports: an optional screenshot can be attached when reporting a post, shown to admins/moderators alongside the report. Reuses the existing upload-validation pattern (2MB limit, image-only), unit-tested.
- Moderation appeals: suspended users (who can't log in to reach Settings at all) can appeal from a new public page linked off the login screen; posting-restricted or warned users appeal from a new "Moderation" section in Settings. Admins get a new "Appeals" tab that shows the appeal message and, on approval, automatically lifts the underlying suspension/restriction/warning and logs it to the audit trail; denying leaves it in place. 11 unit tests cover submission logic (mocked models); an e2e test covers the full lifecycle - blocked login, public appeal, admin approval, working login afterward - and a second e2e test confirms a denied appeal leaves the suspension in place (see Known Gaps for e2e caveats). Caught and fixed a mistake of my own along the way: an edit that accidentally deleted an unrelated required route import, which would have crashed the whole app on boot - caught by actually booting the app with supertest after the change, not just reviewing the diff.
- Structured logging, monitoring/alerts, backup/restore checks, CI, staging, and upload virus scanning: a JSON structured logger replaced ~28 scattered console.log/error calls app-wide; unhandled 5xx errors email an admin address (rate-limited to avoid alert storms); uploads are scanned through a ClamAV daemon's INSTREAM protocol when configured, failing closed by default (`CLAMAV_FAIL_OPEN=true` explicitly opts into fail-open, while `CLAMAV_REQUIRED=true` requires scanner configuration); a GitHub Actions CI workflow runs the unit suite on every push and the full e2e suite against a real MongoDB service container; backup/restore-verification scripts wrap mongodump/mongorestore, with the restore check proving a backup is actually restorable (not just that the file exists) by restoring into a scratch database and sanity-checking it; staging is covered as deployment guidance in a new DEPLOYMENT.md, since it's not something code alone provides. 25 new unit tests across logging/alerting/virus-scanning; the CI workflow was validated by actually parsing it with js-yaml, not just reviewed by eye. Caught two of my own mistakes mid-edit this round (a wrong relative import path, and an accidentally-deleted guard line) by re-running node --check and booting the app after each change rather than trusting the diff - see Known Gaps for what still needs verifying against real infrastructure.
- Search history and account history: recent searches are saved per user (capped at 20, deduped, clearable) and shown on the empty search page; a new `AccountEvent` model logs every security-relevant self-event (logins, password/2FA changes, suspensions/restrictions applied or lifted, warnings, appeals) across every place those already happen, surfaced as a readable timeline in a new Settings > History page.
- RSS feeds for public profiles (`/u/:id/rss.xml`) and communities (`/communities/:slug/rss.xml`), alongside the existing site-wide feed. Building these surfaced a severe, systemic bug - see the entry right below this one - so all three feeds, plus every other post-listing surface in the app, now correctly respect private-community membership.
- CRITICAL FIX - private communities were not actually private: posts in a private community were fully visible to any logged-in user (and via the public API, any anonymous visitor) through the community page, direct post URLs, the main dashboard feed and its tabs, search, profile pages (including the Comments tab, via the parent post), the public `/api/v1/posts` API (including by passing `?community=<id>` directly), and the global RSS feed - and could even be liked/commented/reacted to/replied to/quoted/shared/voted on/reported by non-members, since the shared `canAccessPost` authorization gate used by ~12 interaction endpoints had no community-privacy awareness at all. Fixed comprehensively: one shared, unit-tested utility (`getRestrictedCommunityIds`) applied to every post query listed above, plus a rewritten community-aware `canAccessPost`, plus a proper "members only" state on the community page instead of leaking content. Found while auditing communities per the standing "full check" item. 21 new unit tests plus a full end-to-end regression test proving the leak is closed through every surface (with a sanity check that actual members still see everything normally). Also fixed, found along the way: four of the same "unguarded async handler can hang forever" bugs from earlier this session, in the very same RSS/API endpoints, and a `limit=0` edge case in `/api/v1/posts` that silently fell back to the default instead of clamping to 1.
- API documentation (`API.md`, linked from the README): the public `/api/v1/posts` endpoint (params, response shape, pagination, rate limit, privacy behavior, error shape) and all three RSS feeds. 7 new unit tests verify the documented contract actually holds (limit clamping, invalid-param handling, private-community response shape, pagination cursor logic).
- Direct messages, audited: added the same missing-try/catch fix as everywhere else this session (a DB hiccup while loading an inbox, a thread, or sending a message used to hang the request forever instead of showing an error); and a bigger gap - sending a DM never notified the recipient at all, in-app or via push. Now it does, with its own notification-preference toggle in Settings (default on, like the others). Group chat had the exact same gap (no notification when a message arrives) and got the same fix while this was fresh, plus the same try/catch treatment across all four of its handlers.
- Sign-in/sign-up speed, mail delivery and feed UI pass: mail now goes out over the Gmail API (HTTPS) by default and is never awaited in the request path; sign-in no longer fails on duplicate LoginSession; bcrypt cost is configurable (default 10); DB fails fast; media supports HTTP Range (video seek / iOS playback); feed cards show content + likes/comments/shares/views only with reply/quote/report/edit on the post page; media frames keep each item's aspect ratio; composer is hidden until "Share something"; wider layouts for notifications, messages, settings, profile; CSP-blocked inline confirm() handlers replaced with data-confirm. Not verified in a real browser or against live Gmail/MongoDB - see `npm run mail:test`.
- Staging support in code: `APP_ENV=staging` adds noindex headers, a robots.txt that disallows everything, a visible banner, an email allowlist (`STAGING_MAIL_ALLOWLIST`) and keeps keep-alive off. Unit-tested. See `DEPLOYMENT.md`.
- About-page community charts now use real data: average views per post for new vs. established communities and average weekly posts per community by size tier, computed from published posts in public communities and cached for ten minutes. Unit-tested.
- Async route errors are forwarded to the error handler (Express 4 previously left the request hanging on a rejected promise).
- Settings and profile layouts keep a fixed navigation column and stable width when switching sections.
- Monetization pages and links removed from the frontend for now.
- Translation (posts/comments) tries LibreTranslate first and uses Google Translate only as an explicitly configured paid fallback. Libre failures now fall back correctly, and 401/403 logs explain that `LIBRETRANSLATE_URL` must point to the LibreTranslate service (not the Crowdwide website) and that an API key may be required. Render setup docs use separate services rather than Docker commands in the app build. Unit-tested; live provider access still requires valid deployment configuration.
- Moderators (not just admins) can now resolve appeals, from a new "Pending appeals" section on `/moderator`. Same approve/lift-or-deny logic as the admin console, same audit log and account-history entry. Unit-tested.
